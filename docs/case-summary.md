# 案情摘要与集中确认

交付日期：2026-09-07。

## 产品含义

「案情整理」是律师在案件工作台中的唯一案情录入、阅读和确认入口。系统根据案件要素、案件经过、请求和证据生成可编辑摘要；律师确认后，该文本成为当前案件版本的办案口径。确认不代表争议事实已获证明或对方认可。

底层案件要素和案件经过继续保留，用于来源核验、冲突展示、计算和追溯。摘要确认不会静默改写材料原文或带来源的底层记录。

## 工作流

1. 上传材料并由劳动争议智能体整理到工作台，或在「补充案情信息」中追加结构化记录。
2. 无历史摘要时，页面从当前记录自动形成系统整理版；律师直接编辑。原独立「补充案情信息」入口已移除。
3. 保存底层记录后，摘要基于新的案件版本自动显示更新建议，不覆盖历史确认版。
4. 点击「保存案情」即在一个原子写入中保存摘要草稿、同步可识别的案件要素/经过并推进案件版本。点击「确认当前案情」执行同样的同步，并额外形成律师确认版；不会出现只保存其中一部分的状态。
5. 普通底层记录不再提供复选、批量确认、逐条确认或“确认下一条”。直接编辑底层记录时，顶部才出现「保存底层修改」；正式采用仍由「确认当前案情」统一决定。
6. 当前确认版覆盖普通底层记录，列表显示「当前案情已覆盖」，不要求逐条点击。
7. 冲突、同一要素不同说法、来源变化、事件时间未知和明确的关键缺失仍显示「需关注」，可从摘要直接进入对应底层记录。
7. 新材料或底层记录保存后 revision 变化，旧确认版自动标记待更新；历史版本可展开阅读。

## 生成与边界

- 本期摘要由确定性本地代码从结构化工作台组合，不调用外部大模型；按基本情况、案件经过、请求、证据分节，案件经过按日期排序。
- 每条内容设有摘要长度上限，总摘要不超过 10 万字，避免把全文复制成摘要。
- 律师在摘要中的自由文字修改成为确认版办案口径；可明确识别的结构化内容会同步，但不会修改材料原文、来源引文或伪造证据。需要确定性计算的工资、日期等仍在案件要素中保持结构化值。
- 标准分节内的案件要素和经过，以及空工作台中按既有字段格式填写的内容，会在确认时同步至结构化记录。无法确定映射的自然语言仍保留在摘要，不凭空生成字段。
- 每条结构化记录保存 `modifiedInVersion`，案件要素卡片、列表和详情统一显示「内容版本：案件 Vn」。首次经过新流程保存时，旧数据会按当时案件版本补齐标记，不因此额外推进案件版本。
- 劳动争议智能体在每轮系统上下文和 `casebook read` 中读取摘要；最新确认摘要 revision 与案件一致时优先作为办案口径，底层记录仍用于核验。
- 摘要保存使用案件 revision 和严格单调的 `summaryUpdatedAt` 双重并发校验；即使两个操作发生在同一毫秒，也不会让两个页面静默相互覆盖。

## 代码入口

- `dochaus/lib/casebook-model.ts`：摘要草稿与确认版本模型。
- `dochaus/lib/case-summary.ts`：本地摘要生成、需重点处理规则。
- `services/ingest/src/casebook.ts`：摘要持久化与并发保护。
- `services/ingest/src/server.ts`：`POST /matters/:id/casebook/summary`。
- `apps/web/src/components/CaseSummary.tsx`：阅读、编辑、确认、历史和重点事项。
- `apps/web/src/components/CaseWorkbench.tsx`：工作台主入口与摘要覆盖状态。
- `dochaus/plugin/legal.ts`、`dochaus/tool/casebook.ts`、`dochaus/agent/labor.md`：智能体优先使用当前律师确认版摘要。

## 验证

- `dochaus` 相关 9 项测试通过，包含摘要分节、时间排序和重点事项规则。
- `services/ingest` 工作台 14 项测试通过，包含摘要草稿、确认版本、案件变化失效、并发更新拒绝和无效输入。
- ingest 与 web 类型检查通过，web 生产构建通过（沿用既有 bundle 体积警告）。
- 浏览器使用虚构案件 `matter-7361b4` 验证：确认摘要 V1、重新加载保持、修改底层记录后自动待更新、恢复记录并确认新版本；随后验证草稿保存与并发保护并形成 V3，普通记录显示「摘要已覆盖」。测试记录内容已恢复为原值；未修改真实案件。

## 后续建议

下一阶段可增加“摘要文字变更 → 结构化候选变更”的预览，不应直接反向覆盖带证据来源的记录。工资基数、入离职日期等计算字段仍需独立确认变更建议。
